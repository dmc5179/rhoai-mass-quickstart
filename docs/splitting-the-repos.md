# Splitting values out of the AutoShift fork

Plan, not yet implemented. AutoShift documents a supported way to keep your
configuration out of the code repo —
[`docs/external-values-repo.md`](https://github.com/dmc5179/autoshiftv2/blob/rhoai-maas/docs/external-values-repo.md)
in the fork — and we are not using it. This is what adopting it would take and
how many repositories we actually end up with.

## What the pattern does, and what it does not

It separates **values** from **code**. A multi-source ArgoCD Application takes
two sources: your values repo carries a `ref`, and the chart source reads
`$ref/...` value files from it.

It does **not** move policies out. The doc is explicit:

> `repoURL` is the only place the repository is named. Argo CD injects it into
> `autoshiftGitRepo`, which is where every Application the chart generates
> reads policies from, so a fork points one value at itself and the policies
> follow.

`autoshiftGitRepo` is one value, so **one Application reads policies from
exactly one repository.** Our fourteen policy directories stay in the fork
until upstream takes them.

## The bigger win for us is not the fork rebase

The documented benefit is that upgrading AutoShift stops being a merge
conflict. True, and worth having. But the sharper benefit here is that it
removes a trap we hit this week.

Today `scripts/50-autoshift.sh` runs:

```bash
helm upgrade --install autoshift ./autoshift -n openshift-gitops \
  -f autoshift/values/global.yaml \
  -f autoshift/values/clustersets/hub.yaml \
  -f autoshift/values/clusters/local-cluster.yaml
```

from a **local checkout**. There is no root `autoshift` Application — only the
`autoshift-policies` ApplicationSet that the Helm release creates. So:

- **Policies** are read from Git by the generated Applications. A push deploys.
- **Values** are read from local files by Helm, once, at install time. A push
  does nothing; it takes a `bootstrap`.

That split is why raising `tokenRateLimit` from 100 to 50000 and pushing it
changed nothing on the cluster, and why the live subscription still read
`{"limit":100,"window":"1m"}` afterwards. Under the multi-source Application
ArgoCD fetches the values from Git too, and **the push is the deploy**.

## How many repositories

One new one. The count grows with **sites and workloads**, not with features —
which is the thing worth knowing, since the worry was that adding RHOAI
capability would multiply repos. It does not.

| Repo | Holds | Status |
|---|---|---|
| `dmc5179/autoshiftv2` (fork) | the 14 policy directories, the chart, the ApplicationSet, `_example.yaml` as the label catalog | exists |
| **`site-config`** | `global.yaml`, `clustersets/hub.yaml`, `clusters/local-cluster.yaml` | **new** |
| `dmc5179/rhoai-mass-quickstart` | scripts, CloudFormation, docs | exists, unchanged |
| `dmc5179/hermes-openshift` | one tenant workload, standalone Argo Application | exists, unchanged |

Adding a fifteenth policy touches the fork. Adding a second model touches
`config.openshiftAiModels` in the values repo. Neither adds a repository.

**A second AutoShift Application is possible but is not the tool here.**
`gradual-rollout.md` supports two releases side by side — each gets its own
`policies-<app-name>` namespace, and `versionedClusterSets` owner-guards them
so they cannot fight over a cluster. Each has its own `autoshiftGitRepo`, so
two *policy* repos are technically reachable. That mechanism is designed for
running two **versions** during an upgrade, and using it to host two policy
**collections** is off-label. Keep it in reserve for the contingency where
upstream declines the RHOAI policies.

## What goes in the values repo

Everything we currently edit in the fork that is not a policy:

```
site-config/
  global.yaml
  clustersets/
    hub.yaml            # our 9-label profile, config.openshiftAiModels,
                        # config.modelEgress, tokenRateLimit
  clusters/
    local-cluster.yaml  # generated by scripts/45-autoshift-values.sh
```

`autoshift/values/_example.yaml` **stays in the fork**. It is the label
catalog and the CI contract — the validation suite checks that every
`autoshift.io/` label a policy consumes is declared there. Our values repo
copies from it; it does not replace it.

## What this breaks in our tooling

**`scripts/45-autoshift-values.sh` writes to the wrong place.** It renders
`$AUTOSHIFT_DIR/autoshift/values/clusters/local-cluster.yaml`. After the
migration that file has to land in the values repo, and — this is the part
that changes the workflow — **be committed and pushed before it takes
effect.** Today the script writes a file and `bootstrap` consumes it
immediately.

Net trade: the edit loop gains a git round-trip, and loses an entire class of
"I changed the values and nothing happened". Worth it, but it is a real change
in how the scripts feel, and `45` needs a `--repo` argument and a
commit/push step or an explicit instruction to do it by hand.

**`scripts/autoshift-feature.sh` becomes more important, not less.** The doc
warns that the values repo has no schema:

> A typing error in a label key is not a render error — it produces a label
> nothing consumes.

Our feature script already refuses to enable a group whose prerequisite is off
or whose config is missing. Pointing it at the values repo makes it the only
thing standing between a typo and a silently-unapplied capability.

## Constraints that apply to us specifically

- **`policyGenerator: true` is mandatory in git mode.** Without it the
  PolicyGenerator directories never render and most policies never deploy.
  Setting it `false` fails at render time with an explicit message.
- **Application name ≤ 11 characters**, because the policy namespace is
  `policies-<app-name>`, capped at 20. We use `autoshift` (9) today, giving
  `policies-autoshift` (18). Keep the name to preserve the namespace and avoid
  re-homing every existing policy.
- **The `ref` source must be git**, not Helm/OCI. An OCI chart source is fine
  for source 2; the values source cannot be OCI.
- **Private repo needs ArgoCD credentials registered first**, before the
  Application references it.

## Migration, in the order the doc prescribes

1. Create `site-config` and copy in `global.yaml`, `clustersets/hub.yaml`,
   `clusters/local-cluster.yaml` from the fork.
2. Move anything from the Helm `--set` flags into those files — keep only
   deployment identity (`autoshiftGitRepo`, `autoshiftGitBranchTag`,
   `policyGenerator`) inline.
3. **Prove it is a no-op.** Render both ways and diff:
   ```bash
   helm template autoshift ./autoshiftv2/autoshift \
     -f site-config/global.yaml \
     -f site-config/clustersets/hub.yaml \
     -f site-config/clusters/local-cluster.yaml
   ```
   against the same render from the in-fork files. They must be identical
   before anything is applied.
4. Replace the `helm upgrade --install` in `50-autoshift.sh` with applying the
   multi-source Application, and rework `bootstrap` around it.
5. Confirm ArgoCD resolved both sources:
   ```bash
   oc get applications.argoproj.io autoshift -n openshift-gitops \
     -o jsonpath='{range .spec.sources[*]}{.repoURL}{"\t"}{.ref}{"\n"}{end}'
   ```

Step 3 is the one not to skip. The cluster currently works end to end, and the
migration is only safe if the rendered output is provably unchanged.

## Sequencing against the upstream PRs

Do the values split **after** the upstream PR work, not before. The PRs are
cut from the fork's policy directories, which this migration does not touch —
but it does rewrite `50-autoshift.sh`, regenerate values paths, and change how
the cluster is deployed. Doing both at once means a PR review and a deployment
change failing at the same time with no way to tell which caused what.
